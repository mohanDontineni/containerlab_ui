## Known limitations

- No `/dev/kvm`; all VM-backed vendor templates are unsupported on the current worker.
- No dynamic StorageClass; this installation uses four application-owned retained local PVs on the single node and is not highly available.
- Uploaded images are mirrored into the internal OCI registry with verified manifest digests, but Clabernetes launcher pulls from that registry have not been verified across multiple workers; the current runtime reference remains the content-addressed node-local tag.
- Clabernetes 0.8.0 emitted an auxiliary Alpine puller warning (`exit` executable missing), although launcher pulls, topology readiness, device creation, and traffic all succeeded.
- Shared Containerlab `bridge` network objects are not exposed on this installation: the backend requires a pre-existing Linux bridge on the Kubernetes worker, while Clabernetes is intentionally namespace-isolated. Creating host networking from the application would break that isolation boundary; point-to-point topology links remain fully supported in the GUI.
